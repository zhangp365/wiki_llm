# 跨产品约束 Claude 的方法

> 原文链接: [English Original](https://www.anthropic.com/engineering/how-we-contain-claude)

*Engineering at Anthropic*

发布于 2026年5月25日

随着 Agent 能力的增强，其潜在的"破坏半径"也在扩大。工程问题是如何限制这种影响。以下是我们在为 claude.ai、Claude Code 和 Cowork 构建约束机制时的经验总结。

十二个月前，我们会毫不犹豫地拒绝给予 Claude 足够的访问权限来关闭内部 Anthropic 服务的想法。如今，这种级别的访问权限已成为常态，Anthropic 开发者的生产力因此得到了提高。这些部署的风险有两个组成部分：故障发生的可能性，以及可能造成的损害程度。在安全保障措施和模型训练方面的进展稳步降低了前者；而后者——理论上的破坏半径——只会随着能力和访问范围的扩大而增长。然而，随着 Agent 变得能够完成过去需要一个人甚至一个团队才能完成的工作，不部署的成本变得足够大，以至于风险收益计算严重倾向于采用，只要产品能被设计得安全。工程问题变成了如何限制破坏半径。

当能够对自主 Agent 的相对损害设置边界时——例如通过对其环境的控制——高实用性能力可以推动部署。Claude Mythos Preview 就是这样一个例子：其破坏半径被认为过高，无法在 2026年4月发布。然而，随着防御者加强关键系统并使安全措施成熟，我们期望具有类似能力水平的模型的更广泛发布变得合适——尽管一些风险将始终存在。模型能力是 Agent 部署总体风险的重要因素。

大体上有两种方法可以做到这一点。

第一种是通过人工干预来监督 Agent 的行为。Claude Code 之前通过在每一步要求用户批准来防止 Agent 采取意外行动。理论上这可行，但我们发现这种方法并不可靠。我们的遥测数据显示，用户批准了约 93% 的权限提示。用户看到的批准请求越多，他们对每个请求的关注就越少，随着时间的推移，他们的监督会变得不那么严格。我们最近构建了 Claude Code 自动模式，它自动化更安全的批准以减少这种批准疲劳。尽管如此，漏洞仍然存在——任何概率性防御都有非零的失误率。

第二种限制破坏半径的方法——也是本文的重点——是约束。与其监督 Agent 做什么，我们通过沙箱、虚拟机和出口控制等手段强制执行访问边界，来监督它_能够_做什么。这是 Anthropic 工程团队投入最多精力的地方，也是许多最令人惊讶的安全失败发生的地方。

在过去两年中，我们推出了三个主要的 Agent 产品：claude.ai、Claude Code 和 Claude Cowork。每个产品服务于不同的受众，需要不同的约束架构。本文分享了哪些方法有效、哪些出现了问题，以及我们在 Agent 安全方面的经验教训。

## **三种风险类型，三个防御组件**

Agent 的安全风险分为三类：

**用户滥用：** 用户——无论是恶意还是粗心——指示 Agent 做有害的事情。这包括从要求 Agent 绕过他们觉得烦人的检查，运行他们不理解的危险命令，到指定故意损害的一切。

**模型行为异常：** Agent 采取了没有人要求的有害行动。随着我们的模型改进，它们在大多数行为评估上更加一致，但这并不意味着风险必然缩小。能力较弱的模型更可能误解情况并犯明显错误。能力较强的模型犯的错误较少，但它们也更善于找到通往目标的意外路径，通常通过绕过没有人想到要写下的限制。

在 Anthropic，我们看到 Claude 模型"热心地"逃离沙箱以完成任务，检查 git 历史以找到编码测试的答案，并自发识别其正在运行的基准测试以解密其答案密钥。每个模型都带来了一组新的能力，有时会以意想不到的方式发挥作用。

**外部攻击者：** Agent 通过工具、文件或网络访问等外部向量受到攻击。此类包括提示注入和对 Agent 运行时、编排层或代理的传统攻击。

在构建约束和防御系统时，我们将防御应用于三个主要组件：

**Agent 运行的环境。** 我们通过进程沙箱、VM、文件系统边界和出口控制来约束 Agent 在何处以及如何行动。目标是在 Agent 能够达到的范围内设置硬边界。例如，如果凭证从未进入沙箱，它们就无法被泄露，无论原因是用户、模型找到"创造性"路径还是攻击者。

严格的周边也意味着你可以放松监督。Claude Code 的参考 devcontainer 正是这样存在的，以便 Agent 可以无人值守运行，无需每次操作批准。

**Agent 咨询的模型。** 这里的机制包括系统提示、分类器、探测器和训练修改。由于模型是概率性的，这些只塑造 Agent_倾向于_做什么，而不是它在理论上能够做什么。

这些防御是强大的。在 Gray Swan 的 Agent 红队测试基准上，该基准测试对提示注入的敏感性，Claude Opus 4.7 在单次尝试中将攻击成功率保持在约 0.1%，在 100 次自适应尝试后约为 5-6%。Claude Code 自动模式在执行之前捕获了约 83% 的过度热情行为。然而，即使拥有最先进的防御，模型层的保护永远不会 100% 有效，这就是为什么它不能单独存在。

**Agent 可以到达的外部内容。** MCP 服务器、第三方插件和 Web 搜索工具都从你无法控制的来源向 Agent 的上下文中输入内容。经过审计的连接器与经过审计的数据并不相同——例如，GitHub 连接器可以在通过恶意软件检查的情况下，将受污染的 README 直接加载到模型的上下文中。细致地限制工具权限可以帮助限制破坏半径。例如，具有只读数据库访问权限的 Agent 可以比写入生产环境的 Agent 部署得更广泛。

防御应该重叠并相互补充。当环境防御不可用时，模型层必须弥补差距（这正是 Claude Code 的自动模式的设计目的）。在本地，环境和模型防御可以防范恶意工具输出，但可以通过限制工具的能力和访问来在链条更上游添加防御。

## **约束 Agent 的模式**

专注于环境层，我们描述了三种隔离模式以及它们如何为每个 Claude 平台定制——claude.ai、Claude Code 和 Cowork。我们是在逐渐找到平衡之后才达到每种设计的，即在我们需要 Agent 的能力和用户所需的干预程度之间。

### **模式1：临时容器（claude.ai 代码执行）**

虽然 claude.ai 最著名的是聊天界面，但它也编写和运行代码、生成文件并调用连接器。当 Claude 在 claude.ai 内运行代码时，它在隔离基础设施上的 gVisor 容器中运行。Agent 完全在服务器端；本地机器上不运行代码，文件系统是临时的（每次会话）。破坏半径最小，但 Claude 能做的上限也很低——没有持久的工作空间，无法访问用户的文件系统。

这也使得 claude.ai 面临更传统的威胁模型。我们不是保护用户机器免受 Agent 侵害；我们保护自己的基础设施和每个租户免受彼此侵害。我们在 claude.ai 发布前的工作主要由传统安全工作主导，如网络配置、内部服务身份验证和编排。

这项工作加强了安全领域最古老的教训：最弱的层是你自己构建的层。gVisor 和 seccomp 对抗资源丰富的对手的时间比 Agent AI 存在的时间长得多，因此审查工作集中在我们围绕它们构建的新组件上。我们稍后会回到这一点，因为我们的自定义代理也是在我们后果最严重的故障中出现问题的组件。

### **模式2：人工干预沙箱（Claude Code）**

Claude Code 在用户的机器上运行，可以访问他们的文件系统、shell 和网络。没有这个，编码 Agent 的实用性有限，因此必须找到一种安全地授予这种访问权限的方法。

一种方法是依赖人工干预。这只是 Claude Code 的可行解决方案，因为普通用户是熟悉编码环境的开发者：他们可以阅读 bash，理解 rm -rf 的作用，并且他们已经每周几次从不受信任的来源运行 npm install。所有这些意味着当"允许此操作"对话框弹出时，他们极有可能拥有专业知识来准确评估 Agent 试图做的事情以及涉及的风险。鉴于此，Claude Code 发布时采用最简单的防御：允许读取，要求批准写入、bash 和网络访问。

然而，如前所述，批准疲劳在几周内就出现了。讽刺的是，这意味着最初设计用于提供监督的功能实际上可能产生相反的效果——一些用户可能根本不再关注。为了减轻粗心批准的第一步，我们发布了操作系统级沙箱（macOS 上的 Seatbelt，Linux 上的 bubblewrap），它强化边界：允许读取，在工作空间内允许写入，但默认拒绝网络。在沙箱内，Agent 在没有中断的情况下运行。结果是权限提示减少了 84%，我们开源了运行时，因此边界是可审计的。

我们的匿名使用数据还显示，经验丰富的用户自动批准的频率大约是新用户的两倍，但他们在执行过程中中断 Agent 的频率也更高。经验丰富的用户更有可能只在 Agent 偏离轨道时监督它，而不是限制各个步骤。虽然这可能是人们更喜欢与 Agent 一起工作的自然演变，但这也不可靠，要求用户足够技术化和专注，以便首先注意到偏离。随着模型能力的提高和 Agent 开始编写越来越雄心勃勃的 bash，注意到任何此类偏离变得更加困难。随着用户转向多 Agent 系统，这种方法也不太可能成为有效的监督策略。

#### **我们错过的风险：信任对话框之前的所有内容**

在 2025年中期到 2026年1月期间，我们通过我们的负责任披露计划收到了关于 Claude Code 漏洞的报告。其中三个漏洞针对在用户同意任何事情之前执行的代码。要理解这是如何可能的，考虑最直接的情况：开发者克隆存储库以审查拉取请求，该存储库包含定义钩子的 .claude/settings.json。因为 Claude Code 在启动期间读取项目设置——在呈现标准的"你信任此文件夹吗？"提示之前——攻击者编写并提交的钩子会自动执行。其余情况在结构上看起来相似，即来自尚未受信任目录的输入在建立信任边界之前被解析。

每种情况的修复都有相同的形状：延迟项目本地配置的解析和执行，直到用户接受信任提示之后。如果你正在构建类似的东西，应该像处理来自互联网的任何入站请求一样处理项目打开、配置加载和本地主机监听器。它们不应该仅仅因为感觉本地并在用户同意之前到达而被隐式信任。

#### **我们错过的风险：用户作为注入向量**

2026年2月，在受控内部红队练习期间，研究人员成功地网络钓鱼了一名员工，使其启动带有恶意提示的 Claude Code。网络钓鱼看起来像普通协作——一封"你能帮我运行这个吗？"的电子邮件，附有准备粘贴的提示——提示本身读起来像常规任务说明。但在设置步骤的某个地方，它温和地要求 Claude 读取 ~/.aws/credentials，对内容进行编码，并将它们 POST 到外部端点。在该提示的 25 次重试中，Claude 完成了 24 次泄露。

这是一个_直接_提示注入——攻击者的指令通过用户到达，而不是通过工具输出或获取的内容。我们的模型层防御基于用户意图——当用户是输入指令的人时，对于分类器来说没有什么异常。拿到相同脚本的人类承包商会做同样的事情。

在这种情况下唯一有效的防御是环境，特别是无论意图如何都阻止 POST 的出口控制，以及首先使 ~/.aws 无法到达的文件系统边界。

（当我们在内部 Slack 中分享工作提示以进行讨论时，有人指出一些内部 Agent_读取_Slack。有效负载现在是环境性的。我们向线程添加了金丝雀字符串，以便我们会注意到是否有东西拾取了它。在一个 Agent 读取所有内容的世界中，调查工具也是攻击面。）

### **模式3：本地虚拟机（Claude Cowork）**

Claude Cowork 在用户的桌面上运行，可以访问用户选择的文件夹。因为该平台是为一般知识工作构建的，而不是软件工程，普通用户不太可能熟悉 bash。

因此，人工干预沙箱策略可能无法转移；非技术知识工作者不应被期望判断 bash 咒语，如 find . -name "*.tmp" -exec rm {} \;。当批准例外需要典型用户没有的专业知识时，管理员应该设置一个绝对且始终开启的边界。

为了实现这一点，我们的第一个版本的 Claude Cowork 使用平台的供应商虚拟机管理程序（macOS 上的 Apple Virtualization 框架，Windows 上的 HCS）在完整的虚拟机中运行。VM 有自己的 Linux 内核、自己的文件系统和自己的进程表。用户选择的工作空间和 .claude 文件夹已挂载；主机上的其他任何东西都不可见。凭证保留在主机的钥匙串中，永远不会进入客户机。这种设计防止 Claude 在某个时刻以不一致的方式行为的可能性。受损的 Claude 仍然可能损坏工作空间文件夹内的内容，因此架构设计确保这是它_唯一_能到达的东西（直到用户添加连接器），用户控制那里挂载的内容。

在原始架构中——我们称之为全虚拟机模式——Agent 循环本身在客户机内运行，因此 Claude 作为普通 Linux 用户执行，不知道它被沙箱化。将其与 Claude Code 比较，后者有一个特权进程在沙箱外决定每个命令是否强制执行它；有说服力的注入提示或疲劳的批准点击可以使该进程运行一些非沙箱化的东西。在这里，没有外部进程持有逃生密钥，因此没有组件有权授予例外。

然而，我们很快意识到，在全虚拟机模式下运行整个 Agent 会导致实际问题：VM 启动期间的任何故障都会使 Cowork 不可用。将 Agent 循环移到 VM_之外_，同时在其中保持代码执行，允许 Claude 仍然响应用户并帮助调试问题，而不是在错误时冻结。此变化导致最小的安全影响，因为 VM 仍然对 Agent 执行的代码强制执行文件系统和网络控制。

此外，我们还将本地 MCP 服务器移到 VM 之外。在 VM 内运行它们使它们更难审计，在 VM 更新时创建脆弱的依赖关系问题，并且不支持需要与本地进程（如数据库）交互的 MCP——此类服务器无论如何必须在主机上运行。此变化使 Claude Cowork 与本地 MCP 服务器在 Claude Desktop 中已经工作的方式一致：将它们视为用户可能选择安装的任何软件，并委托管理员决定启用哪些本地 MCP（如果有的话）。远程 MCP 服务器不受影响，因为它们不在用户的机器上运行。

文件系统控制是另一个重要的架构选择。Claude 需要能够访问主机上的_某些_文件才有用，但我们希望最小化破坏半径并向用户提供关于本地文件访问的透明度。我们发现提供不同的文件挂载模式有助于细致地控制风险；Claude Cowork 提供只读、读写和读写无删除。这里的一个潜在问题是符号链接解析必须在路径验证_之前_发生，而不是之后，或者授权文件夹内的符号链接可以指向外部并逃逸。对于企业客户，我们允许管理员通过 MDM 设置中的挂载路径允许列表控制这一点。

#### **我们错过的风险：通过批准域的泄露**

通过批准域泄露的明显例子来自第三方披露。Claude Cowork 的出口允许列表正确地将流量传递到 api.anthropic.com——产品无法在不调用我们自己的 API 的情况下运行。在这种情况下，放置在用户挂载工作空间中的恶意文件携带隐藏指令以及攻击者控制的 API 密钥。Claude 遵循指令，读取工作空间中的其他文件，并使用攻击者的密钥调用 Anthropic 的 Files API。出口代理检查目的地，看到 api.anthropic.com，并让它通过。文件被上传到攻击者的 Anthropic 账户。沙箱工作完美，但数据被泄露了。

此前，我们将允许列表概念化为目的地过滤器，告诉 Claude_这些域可以通信_。但它可能更好地概念化为能力授予。允许列表上任何域可到达的每个函数现在都是攻击面。允许 api.anthropic.com 意味着允许文件上传到任意 Anthropic 账户。

我们使用 VM 内的防御性中间人代理修复了它，它拦截到我们 API 的流量。它只传递携带 VM 自己配置的会话令牌的请求；攻击者嵌入的密钥被代理拒绝。它还阻止启用服务器端获取的标头。代理位于 VM 内而不是我们的服务器上，因为只有 VM 知道来源——从服务器的角度来看，Cowork 请求与任何其他 API 客户端无法区分。

这也是我们自己构建的软件通常是最弱的原理的第二个实例。我们产品中的虚拟机管理程序、seccomp 和 gVisor 一直可靠。我们的自定义允许列表代理是失败的组件。

#### **我们错过的风险：虚拟机隔离也将端点检测软件挡在门外**

在评估 Claude Cowork 时，企业安全团队问："为什么我们的端点检测和响应（EDR）无法看到内部？"答案是，保持 Claude 受限的相同隔离也将基于主机的端点检测和响应挡在门外。从 EDR 的角度来看，Claude Cowork 是一个不透明的虚拟机管理程序进程。它无法检查客户机。

隔离降低了可见性，不透明性对于合规性依赖于端点可见性的团队来说是有问题的。我们当前的缓解措施是使用基于拉的 OTLP 导出，允许管理员在事后检索事件日志，但这与实时监控不同。如果你正在构建类似的东西，请为此对话提前做好预算。

| **环境** | 临时容器 (claude.ai) | 人工干预沙箱 (Claude Code) | 密封虚拟机 (Claude Cowork) |
| --- | --- | --- | --- |
| **成本：隔离开销** | 容器启动 | 低延迟原生沙箱 | 完整虚拟机启动 |
| **成本：用户依赖** | N/A | 必须理解 bash | N/A |
| **风险：破坏半径** | 服务器端容器（由 gVisor + 主机基础设施边界保护） | 本地工作空间 | 挂载工作空间（由 vsock + 虚拟机管理程序边界保护） |

## **信任 Agent 读取的内容**

企业经常询问我们如何保护 MCP 连接。这是一个好问题，但正确的答案比 MCP 更广泛。提供给 Agent 的任何外部资源同时代表两个风险：传统供应链意义上的代码执行风险，以及提示注入向量。传统依赖审计（固定版本、验证签名、审查源代码）解决了第一个，但错过了第二个。

**远程与本地比看起来更重要。** 本地安装的工具是可审计的。你可以阅读代码，固定版本，并知道它不会在你下面改变。远程工具——托管 MCP 服务器、云连接器——可以在你批准后的任何时候改变行为；你的安装时信任决策可能不再适用。我们的连接器目录通过持续审查解决这个问题，但之外的任何东西都应被视为不受信任。首先在恶意工具破坏半径包含的环境中对虚假数据运行它。

**即使工具受信任，工具输出也是攻击面。** 前面提到的 GitHub README 示例正是这种情况；应用于网页的任何输入扫描需要以同样的严格性应用于启用网络的工具结果。尽管这增加了延迟并且不是完美的防御，但我们倾向于实时检查：一旦受污染的工具返回已经引导 Agent 泄露数据，日志只显示成功的、授权的 API 调用。没有事后信号可发现。

在 Claude Code 和 Claude Cowork 中，工具调用通过代理路由，代理强制执行网络和文件策略，可以在内容进入模型上下文之前检查返回值。执行检查的分类器可以是小型、快速的模型；它不需要是进行推理的那个。

## **展望未来**

模型和产品正在快速发展。随着它们的发展，风险也在变化和演变，我们的缓解措施必须跟上以满足它们。

**持久记忆污染。** 跨会话持久保存的 Agent 上下文份额不断增长——这包括产品记忆、CLAUDE.md 文件、挂载工作空间以及定期和长时间运行的 Agent 的状态目录。落在其中任何一个中的注入在每次 Agent 启动时都会重新加载。随着更多 Agent 状态在会话后存活，我们受到经典后期利用意义上的新持久机制的威胁。会话启动时的良好分类器需要变得更加普遍。

**多 Agent 信任升级。** 一方面，子 Agent 可以隔离不受信任的内容，将结构化事实而不是原始文本返回给主 Agent。另一方面，这可能被滥用：如果子 Agent 的输出被视为比原始工具结果更高的信任，因为此类输出来自"我们"，就会引入提示注入的新向量。在多 Agent 系统中，在分配不同信任级别和容易受到信任升级之间存在权衡。

**Agent 身份。** Claude Cowork 对 Agent 身份的回答是具体的：凭证保留在主机的钥匙串中，虚拟机获得每次会话范围缩小的令牌，该令牌可以独立于用户撤销。然而，我们正在努力解决跨平台 Agent 身份的更广泛问题。Agent 应该拥有自己的主体身份，还是应该作为用户的扩展并继承用户的权限？最终，答案可能是两者的混合。

随着 Agent 变得更加有能力，攻击面不断转移。我们看到的失败类型可能会在行业和实验室中重复。我们需要对 Agent 特定安全态势的集体投资，从共享基准测试和披露规范到通用身份标准和跨供应商红队测试。我们在本文中专注于约束，但这只是 Agent 安全图景的一部分。对于治理、可观察性和堆栈的其余部分，请参阅 NIST 关于 AI Agent 身份和授权的项目、由澳大利亚 ACSC 与 CISA 和英国 NCSC 领导的六机构关于采用 Agent AI 的指南，以及 ISO/IEC 42001 AI 管理标准。我们的 Glasswing 计划是一个贡献，但我们期待与合作伙伴和竞争对手在这个关键问题上合作。

## **总结**

简而言之，我们要回到几个原则：

**首先在环境层设计约束，然后在模型层引导行为。** 教会我们最多的两个事件——员工网络钓鱼和第三方允许列表披露——都是出口案例，数据通过允许的路径离开。在每种情况下，模型层无法提供帮助；没有异常可捕获。确定性边界是当所有概率性都失败时被击中的地方。

**将隔离强度与用户的监督能力匹配。** 能阅读 bash 的开发者和不能阅读的知识工作者不在相同的威胁模型上运行。用户是否能够评估 Agent 即将做的事情的问题应该有助于确定约束策略，错误地回答——对专家来说摩擦太大，对非专家来说信任太多——本身就是失败。

**警惕自定义组件。** 经过战斗测试的虚拟机管理程序、系统调用过滤器和容器运行时比你要构建的任何东西都经受住了更多的对手关注。在本文描述的每个部署中，标准原语都有效，而我们围绕它们构建的工作暴露了缺陷。

最终，虽然 Agent 可能是一类新的软件，但它们的系统级交互并不是。它们仍然读取文件、打开套接字并生成进程；这使得使用成熟工具进行约束成为关键可行的防御。随着 AI 的发展，部署的风险收益平衡将不断变化，但对破坏半径设置硬限制通常迫使平衡向正确方向发展。
