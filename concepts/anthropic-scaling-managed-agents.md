# 扩展托管 Agent：将大脑与双手解耦

> 原文链接: [English Original](https://www.anthropic.com/engineering/managed-agents)

*Engineering at Anthropic*

发布于 2026年4月8日

Harness 编码了随着模型改进而过时的假设。托管 Agent（Managed Agents）——我们用于长时间 Agent 工作的托管服务——建立在随着 Harness 变化而保持稳定的接口上。

_通过我们的[文档](https://platform.claude.com/docs/en/managed-agents/overview)开始使用 Claude 托管 Agent。_

工程博客的一个持续主题是如何构建高效 Agent 和为长时间工作设计 Harness。这项工作的一个共同主题是，Harness 编码了关于 Claude 无法独立做什么的假设。然而，这些假设需要经常受到质疑，因为随着模型的改进，它们可能会过时。

作为一个例子，在之前的工作中，我们发现 Claude Sonnet 4.5 会在感觉到其上下文限制接近时过早地完成任务——这种行为有时被称为"上下文焦虑"。我们通过向 Harness 添加上下文重置来解决这个问题。但是当我们在 Claude Opus 4.5 上使用相同的 Harness 时，我们发现这种行为已经消失了。重置变成了死重。

我们期望 Harness 继续发展。因此我们构建了托管 Agent：Claude 平台中的托管服务，通过一小组接口代表你运行长时间 Agent，这些接口旨在比任何特定实现（包括我们今天运行的实现）更持久。

构建托管 Agent 意味着解决计算中的一个老问题：如何为"尚未想到的程序"设计系统。几十年前，操作系统通过将硬件虚拟化为抽象——_进程、文件_——来解决这个问题，这些抽象足够通用，适用于尚不存在的程序。抽象比硬件更持久。`read()` 命令对于它是访问 1970年代的磁盘组还是现代 SSD 是不可知的。顶层的抽象保持稳定，而底层的实现可以自由变化。

托管 Agent 遵循相同的模式。我们将 Agent 的组件虚拟化：会话（发生的一切的仅追加日志）、Harness（调用 Claude 并将 Claude 的工具调用路由到相关基础设施的循环）和沙箱（Claude 可以运行代码和编辑文件的执行环境）。这允许每个实现在不干扰其他实现的情况下交换。我们对这些接口的形状有意见，而不是对后面运行的内容有意见。

## 不要养成宠物

我们首先将所有 Agent 组件放在一个容器中，这意味着会话、Agent Harness 和沙箱都共享一个环境。这种方法有好处，包括文件编辑是直接系统调用，没有服务边界需要设计。

但是通过将所有内容耦合到一个容器中，我们遇到了一个老的基础设施问题：我们养成了_宠物_。在宠物与牲畜的类比中，宠物是一个命名的、手工照料的个体，你无法承受失去它，而牲畜是可以互换的。在我们的例子中，服务器变成了那个宠物；如果容器失败，会话就会丢失。如果容器没有响应，我们不得不将其恢复健康。

照料容器意味着调试无响应的卡住会话。我们唯一的窗口是 WebSocket 事件流，但它无法告诉我们故障发生在_哪里_，这意味着 Harness 中的错误、事件流中的数据包丢失或容器离线都呈现相同的情况。为了弄清楚出了什么问题，工程师必须在容器内打开 shell，但因为那个容器通常还保存用户数据，这种方法本质上意味着我们缺乏调试能力。

第二个问题是，Harness 假设 Claude 处理的任何内容都与它一起生活在容器中。当客户要求我们将 Claude 连接到他们的虚拟私有云时，他们必须要么将他们的网络与我们的网络对等，要么在他们自己的环境中运行我们的 Harness。当我们要将它连接到不同的基础设施时，植入在 Harness 中的假设变成了问题。

## 将大脑与双手解耦

我们到达的解决方案是将我们认为的"大脑"（Claude 及其 Harness）与"双手"（执行操作的沙箱和工具）以及"会话"（会话事件的日志）解耦。每个都变成了一个对其他组件做出很少假设的接口，每个都可以独立失败或替换。

**Harness 离开容器。** 将大脑与双手解耦意味着 Harness 不再生活在容器内。它像调用任何其他工具一样调用容器：`execute(name, input) → string`。容器变成了牲畜。如果容器死亡，Harness 会将失败捕获为工具调用错误并将其传递回 Claude。如果 Claude 决定重试，可以使用标准配方重新初始化新容器：`provision({resources})`。我们不再需要将失败的容器恢复健康。

**从 Harness 故障中恢复。** Harness 也变成了牲畜。因为会话日志位于 Harness 之外，Harness 中的任何东西都不需要在崩溃中幸存。当一个失败时，可以使用 `wake(sessionId)` 重启一个新的，使用 `getSession(id)` 取回事件日志，并从最后一个事件恢复。在 Agent 循环期间，Harness 使用 `emitEvent(id, event)` 写入会话以保持事件的持久记录。

**安全边界。** 在耦合设计中，Claude 生成的任何不受信任代码都在与凭证相同的容器中运行——因此提示注入只需要说服 Claude 读取自己的环境。一旦攻击者拥有这些令牌，他们就可以生成新的、无限制的会话并将工作委托给它们。缩小范围是一个明显的缓解措施，但这编码了关于 Claude 无法使用受限令牌做什么的假设——而 Claude 变得越来越智能。结构修复是确保令牌从未从 Claude 生成的代码运行的沙箱中到达。

我们使用两种模式来确保这一点。身份验证可以与资源捆绑或保存在沙箱外的保险库中。对于 Git，我们在沙箱初始化期间使用每个存储库的访问令牌克隆存储库，并将其连接到本地 git 远程。Git `push` 和 `pull` 在沙箱内工作，Agent 从不处理令牌本身。对于自定义工具，我们支持 MCP 并在安全保险库中存储 OAuth 令牌。Claude 通过专用代理调用 MCP 工具；此代理接受与会话关联的令牌。然后代理可以从保险库获取相应的凭证并调用外部服务。Harness 从不知晓任何凭证。

## 会话不是 Claude 的上下文窗口

长时间任务通常超过 Claude 上下文窗口的长度，解决此问题的标准方法都涉及关于保留什么的不可逆决策。我们在之前的上下文工程工作中探索了这些技术。例如，压缩让 Claude 保存其上下文窗口的摘要，记忆工具让 Claude 将上下文写入文件，实现跨会话学习。这可以与上下文修剪配对，上下文修剪有选择地删除令牌，如旧工具结果或思考块。

但是有选择地保留或丢弃上下文的不可逆决策可能导致失败。很难知道未来的轮次将需要哪些令牌。如果消息通过压缩步骤转换，Harness 会从 Claude 的上下文窗口中删除压缩的消息，这些消息只有在存储的情况下才能恢复。之前的工作已经探索了通过将上下文存储为生活在上下文窗口_之外_的对象来解决此问题的方法。例如，上下文可以是 REPL 中的对象，LLM 通过编写代码来过滤或切片它来编程访问。

在托管 Agent 中，会话提供相同的好处，作为生活在 Claude 上下文窗口之外的上下文对象。但不是存储在沙箱或 REPL 中，上下文持久存储在会话日志中。接口 `getEvents()` 允许大脑通过选择事件流的位置切片来查询上下文。该接口可以灵活使用，允许大脑从上次停止读取的地方继续，在特定时刻之前回退几个事件以查看前因，或在特定操作之前重新读取上下文。

任何获取的事件也可以在传递给 Claude 的上下文窗口之前在 Harness 中转换。这些转换可以是 Harness 编码的任何内容，包括上下文组织以实现高提示缓存命中率和上下文工程。我们将会话中可恢复的上下文存储和 Harness 中的任意上下文管理的关注点分开，因为我们无法预测未来模型将需要什么特定的上下文工程。接口将上下文管理推送到 Harness，只保证会话是持久的且可用于查询。

## 多个大脑，多双手

**多个大脑。** 将大脑与双手解耦解决了我们最早的客户投诉之一。当团队希望 Claude 在自己的 VPC 中针对资源工作时，唯一的路径是将他们的网络与我们的网络对等，因为持有 Harness 的容器假设每个资源都紧邻它。一旦 Harness 不再在容器中，这个假设就消失了。同样的变化带来了性能回报。当我们最初将大脑放在容器中时，这意味着许多大脑需要许多容器。对于每个大脑，在提供容器之前无法进行推理；每个会话都要预先支付完整的容器设置成本。每个会话，即使是永远不会触及沙箱的会话，也必须克隆存储库、引导进程、从我们的服务器获取待处理事件。

那段死时间表示为首次令牌时间（TTFT），它衡量会话在接受工作和产生第一个响应令牌之间等待多长时间。TTFT 是用户最敏锐_感受_到的延迟。

将大脑与双手解耦意味着只有在需要时，大脑才会通过工具调用 `(execute(name, input) → string)` 提供容器。因此不需要容器的会话不会等待容器。推理可以在编排层从会话日志中提取待处理事件后立即开始。使用此架构，我们的 p50 TTFT 下降了约 60%，p95 下降了超过 90%。扩展到多个大脑只是意味着启动许多无状态 Harness，并仅在需要时将它们连接到双手。

**多双手。** 我们还希望能够将每个大脑连接到多双手。实际上，这意味着 Claude 必须推理许多执行环境并决定将工作发送到哪里——这是比在单个 shell 中操作更难的认知任务。我们从单个容器中的大脑开始，因为早期的模型没有这种能力。随着智能的扩展，单个容器反而变成了限制：当该容器失败时，我们失去了大脑到达的每个手的状态。

将大脑与双手解耦使每个手都成为工具 `execute(name, input) → string`：名称和输入进入，返回字符串。该接口支持任何自定义工具、任何 MCP 服务器和我们自己的工具。Harness 不知道沙箱是容器、手机还是 Pokémon 模拟器。因为没有手耦合到任何大脑，大脑可以将手传递给彼此。

## 结论

我们面临的挑战是一个老问题：如何为"尚未想到的程序"设计系统。操作系统通过将硬件虚拟化为足够通用的抽象来持续几十年，这些抽象适用于尚不存在的程序。使用托管 Agent，我们的目标是设计一个系统，以适应未来的 Harness、沙箱或围绕 Claude 的其他组件。

托管 Agent 是具有相同精神的元 Harness，对 Claude 将需要的_特定_ Harness 不持意见。相反，它是一个具有通用接口的系统，允许许多不同的 Harness。例如，Claude Code 是一个优秀的 Harness，我们在各种任务中广泛使用。我们还展示了任务特定的 Agent Harness 在狭窄领域表现出色。托管 Agent 可以容纳其中任何一个，随时间匹配 Claude 的智能。

元 Harness 设计意味着对 Claude 周围的接口有意见：我们期望 Claude 需要操作状态（会话）和执行计算（沙箱）的能力。我们还期望 Claude 需要扩展到多个大脑和多双手的能力。我们设计了接口，以便这些可以在长时间内可靠和安全地运行。但我们对 Claude 需要的大脑或手的数量或位置不做任何假设。
