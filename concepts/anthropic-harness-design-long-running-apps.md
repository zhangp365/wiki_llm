# 长时间应用开发的 Harness 设计

> 原文链接: [English Original](https://www.anthropic.com/engineering/harness-design-long-running-apps)

*Engineering at Anthropic*

发布于 2026年3月24日

Harness 设计是在 Agent 编码前沿性能的关键。以下是我们如何在前端设计和长时间自主软件工程方面进一步推动 Claude。

*由我们 Labs 团队的 Prithvi Rajasekaran 撰写。*

在过去几个月中，我一直在处理两个相互关联的问题：让 Claude 产生高质量的前端设计，以及让它在没有人工干预的情况下构建完整的应用程序。这项工作起源于我们之前在前端设计技能和长时间编码 Agent Harness 方面的努力，我的同事和我通过提示工程和 Harness 设计将 Claude 的性能提高到了远高于基线的水平——但两者最终都遇到了天花板。

为了突破，我寻求了在两个截然不同的领域都有效的新颖 AI 工程方法，一个由主观品味定义，另一个由可验证的正确性和可用性定义。受生成对抗网络（GAN）的启发，我设计了一个具有**生成器**和**评估器** Agent 的多 Agent 结构。构建一个能够可靠地评估输出的评估器——并且有品味——意味着首先开发一组可以将"这个设计好吗？"等主观判断转化为具体的、可评分的术语的标准。

然后我将这些技术应用于长时间自主编码，继承了之前 Harness 工作的两个教训：将构建分解为可管理的块，以及使用结构化工件在会话之间传递上下文。最终结果是一个三 Agent 架构——规划器、生成器和评估器——在多小时的自主编码会话中产生了丰富的全栈应用程序。

## 为什么简单实现会失败

我们之前展示了 Harness 设计对长时间 Agent 编码的有效性有重大影响。在早期的实验中，我们使用初始化 Agent 将产品规范分解为任务列表，以及一个编码 Agent 一次实现一个功能，然后在会话之间传递工件以传递上下文。更广泛的开发者社区已经汇聚到类似的见解，诸如"Ralph Wiggum"方法之类的方法使用钩子或脚本保持 Agent 在连续迭代周期中。

但一些问题仍然持续存在。对于更复杂的任务，Agent 往往会随着时间的推移偏离轨道。在分解这个问题时，我们观察到执行这类任务的 Agent 的两种常见失败模式。

首先，随着上下文窗口的填充，模型往往在冗长任务上失去连贯性（见我们关于上下文工程的文章）。一些模型还表现出"上下文焦虑"，当它们接近认为的上下文限制时，它们开始过早地结束工作。上下文重置——完全清除上下文窗口并启动新的 Agent，结合携带前一个 Agent 状态和下一步的结构化交接——解决了这两个问题。

这与压缩不同，压缩是总结对话的较早部分以便同一个 Agent 可以在缩短的历史上继续进行。虽然压缩保持了连续性，但它不给 Agent 一个干净的状态，这意味着上下文焦虑可能仍然存在。重置提供了一个干净的状态，代价是交接工件必须具有足够的状态以便下一个 Agent 能够干净地接手工作。在我们早期的测试中，我们发现 Claude Sonnet 4.5 表现出足够强烈的上下文焦虑，仅靠压缩不足以实现强大的长任务性能，因此上下文重置成为 Harness 设计的必要条件。这解决了核心问题，但增加了编排复杂性、令牌开销和每次 Harness 运行的延迟。

第二个问题，我们之前没有解决过，是自我评估。当被要求评估他们产生的工作时，Agent 往往通过自信地赞扬工作来回应——即使在人类观察者看来，质量显然平庸。这个问题对于设计等主观任务尤为明显，因为没有相当于可验证软件测试的二元检查。布局感觉是精致还是通用的判断调用，并且 Agent 在给自己的工作评分时可靠地偏向正面。

然而，即使在具有可验证结果的任务上，Agent 在完成任务时有时仍表现出阻碍其性能的判断不佳。将执行工作的 Agent 与判断它的 Agent 分离被证明是解决此问题的强大杠杆。分离本身并不能立即消除那种宽松；评估器仍然是倾向于对 LLM 生成的输出慷慨的 LLM。但调整独立评估器使其怀疑结果证明比使生成器对自己的工作挑剔要容易得多，一旦存在外部反馈，生成器就有具体的东西可以进行迭代。

## 前端设计：使主观质量可评分

我从前端设计实验开始，那里自我评估问题最为明显。在没有任何干预的情况下，Claude 通常倾向于安全、可预测的布局，这些布局在技术上功能正常但在视觉上不引人注目。

两个见解塑造了我为前端设计构建的 Harness。首先，虽然美学不能完全简化为分数——并且个人品味总是会有所不同——它们可以通过编码设计原则和偏好的评分标准来改进。"这个设计美吗？"很难一致回答，但"这是否遵循我们的良好设计原则？"给 Claude 提供了具体的评分依据。其次，通过将前端生成与前端评分分离，我们可以创建一个反馈循环，推动生成器产生更强大的输出。

考虑到这一点，我编写了四个评分标准，我在生成器和评估器 Agent 的提示中都给了它们：

* **设计质量：** 设计是否感觉像一个连贯的整体，而不是部分的集合？这里的强大工作意味着颜色、排版、布局、图像和其他细节结合在一起，创造独特的氛围和身份。
* **原创性：** 是否有自定义决策的证据，还是这是模板布局、库默认值和 AI 生成的模式？人类设计师应该识别故意的创意选择。未修改的库存组件——或 AI 生成的明显迹象，如白色卡片上的紫色渐变——在此失败。
* **工艺：** 技术执行：排版层次、间距一致性、色彩和谐、对比度比率。这是能力检查而不是创意检查。大多数合理的实现在这里默认表现良好；失败意味着基本原理被破坏。
* **功能：** 独立于美学的可用性。用户能否理解界面做什么，找到主要操作，并在没有猜测的情况下完成任务？

我强调设计质量和原创性而不是工艺和功能。Claude 在工艺和功能上已经得分很高，因为所需的技术能力往往对模型来说很自然。但在设计和原创性上，Claude 经常产生的充其量是平淡的输出。标准明确惩罚了高度通用的"AI slop"模式，通过更重地权衡设计和原创性，它将模型推向更多的美学冒险。

我使用带有详细分数分解的少样本示例校准了评估器。这确保评估器的判断与我的偏好一致，并减少迭代中的分数漂移。

我在 Claude Agent SDK 上构建了循环，这保持了编排的简单性。生成器 Agent 首先基于用户提示创建 HTML/CSS/JS 前端。我给评估器 Playwright MCP，这使它能够在评分每个标准和撰写详细评论之前直接与实时页面交互。在实践中，评估器会自己导航页面，截图并仔细研究实现，然后产生其评估。该反馈作为下一次迭代的输入流回生成器。我对每次生成运行 5 到 15 次迭代，每次迭代通常随着对评估器批评的响应将生成器推向更独特的方向。因为评估器主动导航页面而不是评分静态截图，所以每个周期需要真实的挂钟时间。完整运行长达四小时。我还指示生成器在每次评估后做出战略决策：如果分数趋势良好，则改进当前方向；如果方法不起作用，则转向完全不同的美学。

在运行中，评估器的评估在迭代中改善，然后达到平台期，仍有增长空间。一些生成增量细化。其他的在迭代之间采取急剧的美学转变。

标准的措辞以我没有完全预期的方式引导生成器。包括诸如"最好的设计是博物馆质量"之类的短语将设计推向特定的视觉融合，表明与标准相关的提示直接塑造输出的特征。

虽然分数通常在迭代中改善，但模式并不总是完全线性。后来的实现往往整体更好，但我经常看到我更喜欢中间迭代而不是最后一次迭代的情况。实现复杂性也倾向于在各轮中增加，生成器为响应评估器的反馈而追求更雄心勃勃的解决方案。即使在第一次迭代中，输出也明显比根本没有提示的基线好，表明标准和相关语言本身在任何评估器反馈导致进一步细化之前就将模型从通用默认值推开。

在一个值得注意的例子中，我提示模型为荷兰艺术博物馆创建网站。到第九次迭代，它为虚构博物馆产生了一个干净的深色主题登录页面。页面在视觉上经过润色，但大体符合我的期望。然后，在第十个周期，它完全废弃了该方法，将网站重新想象为空间体验：一个具有 CSS 透视渲染的方格地板的 3D 房间，艺术品以自由形式位置挂在墙上，以及画廊房间之间的基于门导航而不是滚动或点击。这是我以前没有从单次生成看到过的那种创造性飞跃。

## 扩展到全栈编码

有了这些发现，我将这种受 GAN 启发的模式应用于全栈开发。生成器-评估器循环自然映射到软件开发生命周期，其中代码审查和 QA 充当与设计评估器相同的结构角色。

### 架构

在我们早期的长时间 Harness 中，我们通过初始化 Agent、一次处理一个功能的编码 Agent 以及会话之间的上下文重置解决了连贯的多会话编码。上下文重置是一个关键解锁：Harness 使用 Sonnet 4.5，表现出前面提到的"上下文焦虑"倾向。创建一个在上下文重置中工作良好的 Harness 是保持模型在任务上的关键。Opus 4.5 在很大程度上自己消除了这种行为，所以我能够完全从此 Harness 中删除上下文重置。Agent 在整个构建中作为一个连续会话运行，Claude Agent SDK 的自动压缩处理沿途的上下文增长。

对于这项工作，我在原始 Harness 的基础上构建了一个三 Agent 系统，每个 Agent 解决我在先前运行中观察到的特定差距。系统包含以下 Agent 角色：

**规划器：** 我们之前的长时间 Harness 要求用户预先提供详细的规范。我想自动化这一步，所以我创建了一个规划器 Agent，它接受简单的 1-4 句提示并将其扩展为完整的产品规范。我提示它在范围上雄心勃勃，并专注于产品上下文和高级技术设计而不是详细的技术实现。这种强调是由于担心，如果规划器试图预先指定详细的技术细节并出错了，规范中的错误会级联到下游实现。限制 Agent 在要生产的可交付成果上并让他们在工作时弄清楚路径似乎更聪明。我还要求规划器找到将 AI 功能编织到产品规范中的机会。（见底部附录中的示例）。

**生成器：** 早期 Harness 的一次一功能方法对范围管理效果很好。我在这里应用了类似的模型，指示生成器在冲刺中工作，一次从规范中选择一个功能。每个冲刺使用 React、Vite、FastAPI 和 SQLite（后来 PostgreSQL）堆栈实现应用程序，指示生成器在每个冲刺结束时自我评估其工作，然后移交给 QA。它还有 git 用于版本控制。

**评估器：** 早期 Harness 的应用程序通常看起来令人印象深刻，但当你实际尝试使用它们时仍有真正的错误。为了捕获这些，评估器使用 Playwright MCP 以用户的方式点击运行的应用程序，测试 UI 功能、API 端点和数据库状态。然后它根据发现的错误和基于前端实验建模的一组标准对每个冲刺进行评分，在这里适用于覆盖产品深度、功能、视觉设计和代码质量。每个标准都有硬阈值，如果任何一个低于它，冲刺失败，生成器得到关于出错的详细反馈。

在每个冲刺之前，生成器和评估器协商冲刺合同：在编写任何代码之前就那块工作的"完成"样子达成一致。这存在是因为产品规范故意是高级的，我想要一步来弥合用户故事和可测试实现之间的差距。生成器提出它将构建的内容以及如何验证成功，评估器审查该提案以确保生成器构建正确的东西。两者迭代直到同意。

通过文件处理通信：一个 Agent 会写入文件，另一个 Agent 会读取它并在该文件内响应或使用新文件响应，前一个 Agent 会依次读取。然后生成器根据约定的协议构建，然后将工作移交给 QA。这保持工作忠实于规范，而不过早过度指定实现。

### 运行 Harness

对于此 Harness 的第一个版本，我使用 Claude Opus 4.5，针对完整 Harness 和单 Agent 系统运行用户提示进行比较。我使用 Opus 4.5，因为这是我开始这些实验时我们最好的编码模型。

我编写了以下提示来生成复古视频游戏制作器：

> *创建一个具有关卡编辑器、精灵编辑器、实体行为和可玩测试模式等功能的 2D 复古游戏制作器。*

下表显示了 Harness 类型、运行长度和总成本。

| **Harness** | **持续时间** | **成本** |
| --- | --- | --- |
| Solo | 20 分钟 | $9 |
| 完整 Harness | 6 小时 | $200 |

Harness 的成本超过 20 倍，但输出质量的差异立即明显。

我期望一个我可以构建关卡及其组件（精灵、实体、平铺布局）然后点击播放以实际玩关卡的界面。我首先打开 solo 运行的输出，初始应用程序似乎符合这些期望。

然而，当我点击时，问题开始出现。布局浪费空间，固定高度的面板留下大部分视口空白。工作流程僵化。尝试填充关卡提示我先创建精灵和实体，但 UI 中没有任何内容引导我朝该顺序发展。更重要的是，实际游戏被破坏。我的实体出现在屏幕上，但没有什么响应输入。深入代码显示实体定义和游戏运行时之间的连线被破坏，表面上没有指示位置。

评估 solo 运行后，我转向 Harness 运行。此运行从相同的单句提示开始，但规划器步骤将该提示扩展为分布在十个冲刺中的 16 功能规范。它远超 solo 运行的尝试。除了核心编辑器和播放模式，规范还需要精灵动画系统、行为模板、音效和音乐、AI 辅助的精灵生成器和关卡设计器，以及具有可共享链接的游戏导出。我给规划器访问我们的前端设计技能，它读取并使用该技能创建应用程序的视觉设计语言作为规范的一部分。对于每个冲刺，生成器和评估器协商定义冲刺的特定实现细节以及将测试以验证完成的可测试行为的合同。

应用程序立即显示比 solo 运行更多的润色和流畅。画布使用整个视口，面板大小合理，界面具有一致的视觉身份，跟踪规范中的设计方向。我在 solo 运行中看到的一些笨拙仍然存在——工作流程仍然不清楚你应该在尝试填充关卡之前构建精灵和实体，我必须通过四处点击来弄清楚。这读作基础模型的产品直觉的差距，而不是 Harness 设计要解决的东西，尽管它确实建议了 Harness 内定向迭代可以进一步提高输出质量的地方。

通过编辑器，新运行相比 solo 的优势变得更加明显。精灵编辑器更丰富、功能更全，工具调色板更干净，颜色选择器更好，缩放控件更可用。

因为我要求规划器将 AI 功能编织到其规范中，应用程序还带有内置 Claude 集成，让我可以通过提示生成游戏的不同部分。这显著加快了工作流程。

最大区别在于播放模式。我实际上能够移动我的实体并玩游戏。物理有一些粗糙边缘——我的角色跳到平台上但最终与它重叠，感觉直观上是错的——但核心东西工作，这是 solo 运行没有管理的。四处移动后，我确实遇到了 AI 游戏关卡构建的一些限制。有一堵大墙我无法跳过，所以我被困住了。这建议了一些常识性改进和边缘情况，Harness 可以处理以进一步改进应用程序。

阅读日志，很明显评估器保持实现与规范一致。每个冲刺，它遍历冲刺合同的测试标准并通过 Playwright 练习运行的应用程序，对偏离预期行为的任何内容提交错误。合同是细粒度的——仅冲刺 3 就有 27 个标准覆盖关卡编辑器——并且评估器的发现足够具体，无需额外调查即可采取行动。下表显示了我们评估器识别的几个问题示例：

| **合同标准** | **评估器发现** |
| --- | --- |
| 矩形填充工具允许点击拖动以使用选定的平铺填充矩形区域 | **失败** — 工具仅在拖动开始/结束点放置平铺而不是填充区域。`fillRectangle` 函数存在但未在 mouseUp 上正确触发。 |
| 用户可以选择和删除放置的实体生成点 | **失败** — `LevelEditor.tsx:892` 中的删除键处理程序要求同时设置 `selection` 和 `selectedEntityId`，但点击实体仅设置 `selectedEntityId`。条件应为 `selection || (selectedEntityId && activeLayer === 'entity')`。 |
| 用户可以通过 API 重新排序动画帧 | **失败** — `PUT /frames/reorder` 路由在 `/{frame_id}` 路由之后定义。FastAPI 将 'reorder' 匹配为 frame_id 整数并返回 422："无法将字符串解析为整数。" |

让评估器在此级别表现需要工作。开箱即用，Claude 是一个糟糕的 QA Agent。在早期运行中，我看着它识别合法问题，然后说服自己决定它们并不重要并批准工作。它还倾向于肤浅测试，而不是探测边缘情况，因此更微妙的错误经常漏掉。调整循环是阅读评估器的日志，找到其判断与我的判断不同的示例，并更新 QA 的提示以解决这些问题。经过几轮此开发循环后，评估器以我认为合理的方式评分。即使那时，Harness 输出显示了模型 QA 能力的限制：小布局问题、某些地方感觉不直观的交互，以及评估器未彻底练习的更深层嵌套功能中的未发现错误。显然有更多验证空间可以通过进一步调整捕获。但与 solo 运行相比，应用程序的核心功能根本不起作用，提升是明显的。

### 迭代 Harness

第一组 Harness 结果令人鼓舞，但它也庞大、缓慢且昂贵。逻辑上的下一步是找到简化 Harness 而不降低其性能的方法。这部分是常识，部分是一个更一般原则的函数：Harness 中的每个组件编码关于模型无法独立做什么的假设，这些假设值得压力测试，既因为它们可能不正确，也因为随着模型改进，它们可能会迅速过时。我们的博客文章《构建高效 Agent》将底层思想框架为"找到尽可能简单的解决方案，仅在需要时增加复杂性"，这是任何维护 Agent Harness 的人一致显示的模式。

在我第一次简化尝试中，我彻底削减了 Harness 并尝试了一些创意新想法，但我无法复制原始的性能。也很难说出 Harness 设计的哪些部分实际上是承重的，以及以何种方式。基于那次经历，我转向更系统化的方法，一次删除一个组件并审查其对最终结果的影响。

在我进行这些迭代循环时，我们还发布了 Opus 4.6，这进一步减少了 Harness 复杂性的动机。有充分的理由期望 4.6 需要比 4.5 更少的脚手架。从我们的发布博客："[Opus 4.6] 更仔细地规划，更长时间地维持 Agent 任务，可以在更大的代码库中更可靠地操作，并具有更好的代码审查和调试技能以捕获自己的错误。"它还在长上下文检索方面显著改进。这些都是 Harness 构建以补充的能力。

#### 移除冲刺结构

我首先完全移除冲刺结构。冲刺结构有助于将工作分解为块，以便模型连贯地工作。鉴于 Opus 4.6 的改进，有充分的理由相信模型可以本地处理工作，而无需这种分解。

我保留了规划器和评估器，因为每个都继续增加明显价值。没有规划器，生成器范围不足：给定原始提示，它会开始构建而无需首先规范其工作，最终创建比规划器创建的功能更少的应用程序。

移除冲刺结构后，我将评估器移到运行结束时的一次通过，而不是每次冲刺评分。由于模型更强大，它改变了评估器对某些运行的重要性，其有用性取决于任务相对于模型可以可靠独立完成的内容的位置。在 4.5 上，该边界接近：我们的构建处于生成器可以独立良好工作的边缘，评估器在整个构建中捕获有意义的问题。在 4.6 上，模型的原始能力增加，因此边界向外移动。过去需要评估器检查以连贯实现的任务现在通常在生成器独立处理的范围内，对于该边界内的任务，评估器成为不必要的开销。但对于仍然处于生成器能力边缘的构建部分，评估器继续提供真正的提升。

实际含义是，评估器不是固定的是或否决策。当任务超出当前模型可以可靠独立完成的内容时，它值得成本。

除了结构简化，我还添加了提示以改进 Harness 将 AI 功能构建到每个应用程序中，特别是让生成器构建一个适当的 Agent，可以通过工具驱动应用程序自己的功能。这需要真正的迭代，因为相关知识足够新，Claude 的训练数据稀疏覆盖它。但通过足够的调整，生成器正确地构建了 Agent。

#### 更新 Harness 的结果

为了测试更新的 Harness，我使用以下提示生成数字音频工作站（DAW），这是用于创作、录制和混合歌曲的音乐制作程序：

> *使用 Web Audio API 在浏览器中构建功能齐全的 DAW。*

运行仍然冗长且昂贵，大约 4 小时和 $124 的令牌成本。

大部分时间用于构建器，它在没有 Opus 4.5 所需的冲刺分解的情况下连贯运行超过两小时。

与之前的 Harness 一样，规划器将单行提示扩展为完整规范。从日志中，我可以看到生成器模型很好地规划了应用程序和 Agent 设计，连接 Agent，并在移交给 QA 之前测试它。

尽管如此，QA Agent 仍然捕获了真正的差距。在它的第一轮反馈中，它指出：

> 这是一个强大的应用程序，具有出色的设计保真度、坚实的 AI Agent 和良好的后端。主要的失败点是功能完整性——虽然应用程序看起来令人印象深刻，AI 集成效果很好，但几个核心 DAW 功能仅显示而没有交互深度：片段无法在时间线上拖动/移动，没有乐器 UI 面板（合成器旋钮、鼓垫），没有视觉效果编辑器（EQ 曲线、压缩计）。这些不是边缘情况——它们是使 DAW 可用的核心交互，规范明确要求它们。

在它的第二轮反馈中，它再次捕获了几个功能差距：

> 剩余差距：
> - 音频录制仍然是仅存根（按钮切换但没有麦克捕获）
> - 边缘拖动的片段调整大小和片段拆分未实现
> - 效果可视化是数字滑块，不是图形（没有 EQ 曲线）

当生成器自己处理时，它仍然可能遗漏细节或存根功能，QA 在捕获那些最后里程问题以供生成器修复方面仍然增加价值。

## 下一步

随着模型继续改进，我们可以粗略期望它们能够工作更长时间，并在更复杂的任务上工作。在某些情况下，这意味着模型周围的脚手架随着时间的推移不那么重要，开发人员可以等待下一个模型并看到某些问题自行解决。另一方面，模型越好，开发 Harness 以完成模型在基线时无法完成的复杂任务的空间就越大。

考虑到这一点，这项工作中的几个教训值得继续前进。始终良好的实践是针对你正在构建的模型进行实验，在现实问题上读取其跟踪，并调整其性能以实现期望的结果。在处理更复杂的任务时，分解任务并对问题的每个方面应用专用 Agent 有时会有提升空间。当新模型落地时，通常良好的做法是重新检查 Harness，剥离对性能不再承重的部分并添加新部件以实现以前可能无法实现的更大能力。

从这项工作中，我的信念是，有趣 Harness 组合的空间不随着模型改进而缩小。相反，它会移动，AI 工程师有趣的工作是继续找到下一个新颖的组合。
