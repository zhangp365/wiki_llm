# 关于 Claude Code 质量报告的最新更新

> 原文链接: [English Original](https://www.anthropic.com/engineering/april-23-postmortem)

*Engineering at Anthropic*

发布于 2026年4月23日

我们追踪了最近关于某些用户的 Claude 响应恶化的报告。我们将这些报告追溯到影响 Claude Code、Claude Agent SDK 和 Claude Cowork 的三个独立变化。API 未受影响。

截至 4月20日（v2.1.116），所有三个问题现已解决。

在本文中，我们解释了我们发现的内容、我们修复的内容，以及我们将采取的不同措施以确保类似问题不太可能再次发生。

我们非常认真地对待关于质量下降的报告。我们从未故意降低我们的模型，我们能够立即确认我们的 API 和推理层未受影响。

经过调查，我们确定了三个不同的问题：

1. 3月4日，我们将 Claude Code 的默认推理努力从 `high` 更改为 `medium`，以减少一些用户在 `high` 模式下看到的非常长的延迟——足以使 UI 看起来冻结。这是一个错误的权衡。4月7日，在用户告诉我们他们更愿意默认更高智能并选择更低努力来处理简单任务后，我们恢复了此更改。这影响了 Sonnet 4.6 和 Opus 4.6。
2. 3月26日，我们发布了一个更改，以清除空闲超过一小时的会话中的 Claude 旧思考，以减少用户恢复这些会话时的延迟。一个错误导致这种情况在会话的其余部分的每一轮都持续发生，而不是只发生一次，这使得 Claude 看起来健忘和重复。我们在 4月10日修复了它。这影响了 Sonnet 4.6 和 Opus 4.6。
3. 4月16日，我们添加了系统提示指令以减少冗长。与其他提示更改结合，它损害了编码质量，并于 4月20日恢复。这影响了 Sonnet 4.6、Opus 4.6 和 Opus 4.7。

因为每个更改在不同时间表上影响了不同流量片段，所以总体影响看起来像广泛、不一致的下降。虽然我们在 3月初开始调查报告，但起初很难将它们与用户反馈的正常变化区分开来，我们的内部使用和评估最初也没有复制识别出的问题。

这不是用户应该期望从 Claude Code 获得的体验。截至 4月23日，我们正在为所有订阅者重置使用限制。

## 更改 Claude Code 的默认推理努力

当我们在 2月在 Claude Code 中发布 Opus 4.6 时，我们将默认推理努力设置为 `high`。

此后不久，我们收到用户反馈，Claude Opus 4.6 在高努力模式下偶尔会思考太长时间，导致 UI 看起来冻结，并为这些用户导致不成比例的延迟和令牌使用。

一般来说，模型思考时间越长，输出越好。努力级别是 Claude Code 让用户设置这种权衡的方式——更多思考与更低延迟和更少的使用限制命中。当我们为模型校准努力级别时，我们会考虑这种权衡，以便选择测试时计算曲线上给人们最佳范围选择的点。在产品层，我们选择沿此曲线设置哪个点作为我们的默认值，这是我们作为努力参数发送到 Messages API 的值；然后我们通过 `/effort` 提供其他选项。

在我们的内部评估和测试中，中等努力在大多数任务中实现了略低的智能，延迟显著降低。它也没有遭受相同的偶发非常长尾思考延迟问题，并且它有助于最大化用户的使用限制。因此，我们推出了一个更改，使中等成为默认努力，并通过产品内对话框解释了基本原理。

推出后不久，用户开始报告 Claude Code 感觉不太智能。我们发布了多个设计迭代，以使当前努力设置更清晰，以便提醒人们他们可以更改默认值（启动通知、内联努力选择器和带回 ultrathink），但大多数用户保留了中等努力默认值。

在听到更多客户的反馈后，我们在 4月7日扭转了这一决定。所有用户现在默认为 Opus 4.7 的 `xhigh` 努力和所有其他模型的 `high` 努力。

## 删除先前推理的缓存优化

当 Claude 推理任务时，该推理通常保留在对话历史中，以便在每个后续轮次中，Claude 可以看到它为什么进行了编辑和工具调用。

3月26日，我们发布了旨在对此功能进行效率改进的内容。我们使用提示缓存使用户的连续 API 调用更便宜、更快。Claude 在发出 API 请求时将输入令牌写入缓存，然后在一段不活动后，提示从缓存中逐出，为其他提示腾出空间。缓存利用率是我们仔细管理的东西（更多关于我们的方法）。

设计应该很简单：如果会话空闲超过一小时，我们可以通过清除旧的思考部分来减少用户恢复该会话的成本。由于请求无论如何都是缓存未命中，我们可以从请求中修剪不必要的消息，以减少发送到 API 的未缓存令牌数量。然后我们将恢复发送完整的推理历史。为此，我们使用了 `clear_thinking_20251015` API 标头以及 `keep:1`。

实现有一个错误。不是清除思考历史一次，而是在会话的其余部分的每一轮都清除它。会话一旦超过空闲阈值，该过程的其余部分的每个请求都告诉 API 只保留最近的推理块并丢弃其之前的所有内容。这复合了：如果你在 Claude 工具使用中间发送后续消息，那会在损坏的标志下开始新轮，所以即使是当前轮的推理也被删除。Claude 会继续执行，但越来越没有记住它选择做正在做的事情的原因。这表现为人们报告的健忘、重复和奇怪的工具选择。

因为这会从后续请求中连续删除思考块，这些请求也导致缓存未命中。我们认为这就是推动使用限制比预期更快消耗的单独报告的原因。

两个不相关的实验使我们在一开始很难重现这个问题：仅限内部的服务器端实验，与消息排队相关；以及我们如何显示思考的正交变化抑制了大多数 CLI 会话中的这个错误，所以即使测试外部构建也没有捕获它。

这个错误位于 Claude Code 的上下文管理、Anthropic API 和扩展思考的交叉点。它引入的变化通过了多次人工和自动代码审查，以及单元测试、端到端测试、自动验证和内部测试。结合这只发生在角落情况（陈旧会话）以及重现问题的难度，我们花了一周多的时间才发现并确认根本原因。

作为调查的一部分，我们使用 Opus 4.7 对有问题的拉取请求进行了代码审查的回溯测试。当提供收集完整上下文所需的代码存储库时，Opus 4.7 发现了错误，而 Opus 4.6 没有。为了防止这种情况再次发生，我们现在正在为代码审查的上下文支持额外的存储库。

我们在 4月10日的 v2.1.101 中修复了此错误。

## 减少冗长的系统提示更改

我们最新的模型 Claude Opus 4.7 相对于其前身有一个明显的行为怪癖：正如我们在发布时所写，它倾向于相当冗长。这使其在困难问题上更智能，但它也产生更多的输出令牌。

在我们在 4月发布 Opus 4.7 之前的几周，我们开始为准备调整 Claude Code。每个模型的行为略有不同，我们在每次发布之前花时间优化 Harness 和产品。

我们有许多工具可以减少冗长：模型训练、提示和改进产品中的思考 UX。最终我们使用了所有这些，但系统提示的一个添加对 Claude Code 中的智能产生了过大影响：

> *"长度限制：保持工具调用之间的文本 ≤25 个词。保持最终响应 ≤100 个词，除非任务需要更多细节。"*

经过数周的内部测试和我们运行的评估集中没有退化，我们对更改充满信心，并于 4月16日与 Opus 4.7 一起发布。

作为此调查的一部分，我们使用更广泛的评估集运行了更多的消融实验（从系统提示中删除行以了解每行的影响）。其中一项评估显示 Opus 4.6 和 4.7 都下降了 3%。我们作为 4月20日发布的一部分立即恢复了提示。

## 展望未来

我们将采取几项不同的措施来避免这些问题：我们将确保更多的内部员工使用 Claude Code 的确切公共构建（而不是我们用来测试新功能的版本）；我们将改进我们内部使用的代码审查工具，并向客户发布此改进版本。

我们还对系统提示更改添加了更严格的控制。我们将为 Claude Code 的每个系统提示更改运行广泛的每个模型评估套件，继续消融以了解每行的影响，我们构建了新工具使提示更改更容易审查和审计。我们还向我们的 CLAUDE.md 添加了指导，以确保模型特定的更改针对它们针对的特定模型。对于任何可能与智能进行权衡的更改，我们将添加浸泡期、更广泛的评估套件和渐进推出，以便我们更早捕获问题。

我们最近在 X 上创建了 @ClaudeDevs，为我们提供深入解释产品决策及其背后理由的空间。我们将在 GitHub 上的集中线程中分享相同的更新。

最后，我们要感谢我们的用户：使用 `/feedback` 命令与我们分享问题的人（或在线发布具体、可重现示例的人）是最终使我们能够识别和修复这些问题的人。今天我们正在为所有订阅者重置使用限制。

我们非常感谢您的反馈和您的耐心。
